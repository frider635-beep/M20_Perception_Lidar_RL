# Recovery adjustments and guarded 30000-update session

Current instruction, 2026-11-17: **4096 environments, 100 updates between evaluations, and no automatic stop for behavior-evaluation failures**. Valid retention/repair failures, including falls, stalls and lost ascent completion, are logged and learning continues with the same policy and optimizer. Capability losses receive prominent alerts. Invalid evaluation data, evaluator/runtime errors, exhausted disk/RAM reserves, and user interrupts can still terminate the process. No training is started by this revision. The requested target remains 30000 additional PPO updates, with a command for manual launch below. The original `interview_prep/model_35300.pt` remains the default source and frozen reference; historical candidates remain separate files.

Recovery now keeps velocity rewards independent of flat-posture cost. New flat costs are bounded to at most 1.5 reward/second in total; compact straight movement receives a separate positive quality term that is zero when a commanded robot stands still. Zero-yaw/zero-lateral flat stability and 20% pure-forward/10% stationary non-stair samples are restored. B1 and subsequent overshoot have finite budgets. Progress high-water marks cannot decrease during inactive intervals, preventing retreat/re-advance credit. A missed tread remains a failed sequence but does not remove future real-progress rewards.

The reference replay v2 is 6724 policy-active observations from this host's 12 original-model MuJoCo cases, including Z/C/8 transitions. Physical case/phase labels control balanced sampling and selective action anchoring; missing stair features never imply flat terrain. Flat leg motion and wheel differential corrections have weaker reference penalties while common wheel drive is retained. Early actor layers and action standard deviation remain frozen. The native 63-observation/16-action interface is unchanged.

Validation has separate retention and repair gates. Retention compares each candidate against the original-model results: complete ascent, no fall/bypass/new stall, at least 95% baseline world-route speed, and bounded regression of local progress/yaw/lateral displacement. Repair additionally requires front-wheel every-tread support, sustained four-wheel upright top support and clearance, posture, speed, C-idle yaw and moving yaw limits. Rear-wheel tread sequences are recorded but are not a hard every-tread condition. New route speed is horizontal world-route progress; older body-x speed is also recorded. Neither gate establishes real-robot readiness.

`scripts/train_m20_v111_guarded.sh` starts one persistent Isaac/RSL process. It preserves optimizer state across 100-update segments and pauses learning for serial CPU MuJoCo evaluation. Evaluator exit 2 with a valid failed behavior report prints the failures and continues the next segment. Thresholds still determine whether each model passed; continuation never marks a failed model as accepted. Baseline schema/provenance are checked before Isaac startup, and its hash is checked between segments. The session status records actual additional updates separately from historical checkpoint iteration numbers.

The workstation ledger permits 30000 total guarded updates. Both the default and maximum evaluation interval are 100 updates; an explicit shorter interval remains supported. Its default and maximum environment count are now 4096, matching the Recovery environment and guarded launcher defaults. Ordinary unguarded repair-stage iteration limits remain in force. A 6 GiB disk and 6 GiB available-RAM reserve are checked before each segment. Checkpoints, evaluation metrics and support sequences are saved at every segment boundary. The existing trajectory condition retains full trajectories only when the completed update count is divisible by 250. With the default 100-update segments, this means full trajectories every 500 updates, while intervening evaluations retain summaries and support sequences. No historical user files are deleted.

The 4096-environment configuration has now completed one actual 100-update segment. Its new continue-after-failure behavior has CPU tests and has not been exercised in an additional Isaac/PPO run. With rollout 96, each update collects 393216 transitions; four minibatches give 98304 samples per minibatch, with three epochs and 12 optimizer steps per update. One evaluation interval therefore contains 39321600 transitions and 1200 optimizer steps. Compared with the previous 8192-environment, 25-update interval, this gives twice the transitions and four times the optimizer steps before evaluation. The learning rate remains 1e-5 and the reference loss remains a mean over 256 sampled observations per optimizer step. Changing the environment count does not automatically change that loss coefficient. Longer training permits recovery from temporary regressions and also permits further regression; retaining every segment checkpoint and honest acceptance results preserves the evidence needed to select a model.

The GitHub update includes the unchanged 12-case baseline results and provenance manifests in `data/m20_recovery/baseline_v2/`. Historical full trajectories remain local. From the new host's actual repository root, manually launch with a new session directory:

```bash
cd M20_perception_Lidar_rl
export M20_PYTHON=python3  # Activate the target host Isaac Lab environment first.
M20_SESSION="$PWD/artifacts/recovery_4096_$(date +%Y%m%d_%H%M%S_%N)"
mkdir -p "$M20_SESSION"
set -o pipefail
bash scripts/train_m20_v111_guarded.sh \
  --total-updates 30000 --segment-updates 100 --num_envs 4096 \
  --baseline-results "$PWD/data/m20_recovery/baseline_v2/results.json" \
  --output "$M20_SESSION" 2>&1 | tee "$M20_SESSION/launch.log"
```

The target is additional updates 35301 through 65300. Behavior failures do not end that target. The standalone acceptance tool retains its 0/2 pass/fail interface; the training loop consumes valid exit-2 reports, records them and continues. Completing the requested updates exits 0 even when model acceptance failed; process success means the requested computation finished, not that the model is repaired. Actual runtime errors retain a traceback and nonzero exit status.

`status.json` records `behavior_failure_policy: record_and_continue`, completed updates, `last_checkpoint`, `last_retained_checkpoint`, `last_repair_passed_checkpoint` when one exists, and a `retention_history` of failed evaluations. Latest retention and repair booleans always reflect the actual report. A run with any retention failure ends as `completed_with_retention_failures`; a later recovery does not erase that history. `latest_metrics.json` and `metrics_history.jsonl` retain per-case speed against the command/baseline, flat reach, idle/moving yaw, lateral displacement, stair support, falls and stalls. The monitor highlights capability losses without stopping training. `run_dir.txt` points to the RSL logs and saved weights. An interrupted segment may have logged individual updates without reaching a saved/evaluated segment boundary.

Add `--check-only` to the same launcher to validate limits, model/replay and baseline inputs without starting Isaac or PPO. It does not test GPU capacity. To monitor a manually started session in another terminal, use its actual session path:

Headless repair workers now replace Isaac's SIGINT/SIGTERM handlers immediately after AppLauncher returns. Ctrl+C or SIGTERM unwinds Python, records `stopped_by_user` if the session has started, and cancels the acceptance process group including its benchmark descendants. Cleanup has a 20-second deadline; a second interrupt terminates immediately. Normal interrupt exit codes are 130/143; the native cleanup deadline terminates via SIGALRM (shell status 142). No incomplete or unvalidated candidate is promoted. These signal paths have CPU subprocess tests; native 8192-environment shutdown is not runtime-verified. Interrupts during AppLauncher construction still use Isaac's own handlers.
